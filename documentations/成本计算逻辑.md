
# 适用场景

| 版本  | 适用场景                              |
| --- | --------------------------------- |
| 旧版  | 聚合架构 (agg) / 单 GPU 类型实验           |
| 新版  | 分离架构 (disagg) / 混合 GPU 类型 / 多副本部署 |

# 新旧版本对

| 资源参数 | 旧版处理 | 新版处理 | 影响说明 |
|----------|----------|----------|----------|
| `replicas` | 完全忽略 | 显式使用：`total_nodes = replicas × nodes_per_replica` | replica>1 时成本按"每副本独占"保守估算，避免低估 |
| `workers` / `gpus_per_worker` | 完全忽略 | 显式使用：<br>`p_gpus = p_workers × p_gpus_per_worker`<br>`d_gpus = d_workers × d_gpus_per_worker` | 能识别 P/D 资源不对称场景（如 P=10卡, D=2卡） |
| 缺失参数回退 | 无 | 若 `p_gpus_worker` 缺失，尝试用 `(p)tp × (p)pp × (p)dp` 反推 | 增强鲁棒性，减少因字段缺失导致的计算失败 |

## 新版计算步骤（分离架构

```text
# Step 1: 先算单套服务（replica=1）的 GPU 需求
P_single_replica_gpus = prefill_workers × p_gpus_per_worker
D_single_replica_gpus = decode_workers × d_gpus_per_worker

# Step 2: 计算单套的节点数（单机 8 卡）
P_single_replica_nodes = ceil(P_single_replica_gpus / 8)
D_single_replica_nodes = ceil(D_single_replica_gpus / 8)

# Step 3: 乘以 replica 数量得到总节点数
P_total_nodes = P_single_replica_nodes × replicas
D_total_nodes = D_single_replica_nodes × replicas
total_nodes = P_total_nodes + D_total_nodes

# Step 4: 成本 = P 节点数 × P 机型租金 + D 节点数 × D 机型租金
total_monthly_cost = P_total_nodes × P_月租金 + D_total_nodes × D_月租金
```

# 示例

- 假设配置：`prefill_workers=2`, `decode_workers=2`, `p_gpus_per_worker=4`, `d_gpus_per_worker=8`, `replicas=2`
	- 单套 P GPU：2 × 4 = 8 → P 单套节点：ceil(8/8) = **1 节点**
	- 单套 D GPU：2 × 8 = 16 → D 单套节点：ceil(16/8) = **2 节点**
	- replica=2 → P: 1×2=2, D: 2×2=4
	- **总计：2 + 4 = 6 节点**
-  边界情况：
	- 假设所有 GPU 类型相同（同为 A100 或同为 L40）
	- 假设机器都是 8 卡机型
	- 异构场景（P 用 L40，D 用 A100）需分别计算后再汇总节点
	- 实际节点数还受机架拓扑、NVLink 连接性影响

# 成本计算方法
## Worker：逻辑并行单元

Worker 是「任务调度的最小逻辑单位」，不是物理节点。

|实验名|Prefill Workers|Decode Workers|解读|
|---|---|---|---|
|`l40_p_a100_d_long_disagg`|5|3|Prefill 阶段用 5 个逻辑单元并行处理请求，Decode 阶段用 3 个单元并行生成|
|`a100_long_disagg`|2|1|Prefill 用 2 个单元，Decode 用 1 个单元（因为 Decode TP=8 已占满单机）|

Worker 数的作用：
- 增加 `prefill_workers` → 提升 并发 Prompt 处理能力（降低 TTFT）
- 增加 `decode_workers` → 提升 并发 Token 生成能力（提升 Throughput）

> ⚠️ 注意：不同框架对 Worker 的定义可能不同。vLLM 中一个 Worker 通常管理 1 张 GPU（或 TP 组），Ray 中 Worker 是执行 actor，Kubernetes 中通常 Pod = Worker。
---
## GPU/Worker：单 Worker 的资源粒度

决定「一个 worker 能跑多大模型」或「单请求的并行加速比」。

```python
# 计算公式（当前实验 pp=1）
gpus_per_worker = tp × pp = tp
```

|实验名|p_gpus_worker|prefill_tp|解读|
|---|---|---|---|
|`l40_p_a100_d_long_disagg`|2|2|每个 Prefill worker 用 2 张 L40，模型被切分到 2 卡上做张量并行|
|`a100_long_disagg`|4 (P) / 8 (D)|4 (P) / 8 (D)|Prefill worker 用 4 卡 TP，Decode worker 用 8 卡 TP（单机满配）|

GPU/Worker 的作用：
- 值越大 → 单 worker 能加载 更大参数量的模型
- 但 >8 时会跨节点，通信开销剧增，推理延迟上升 ⚠️

> ⚠️ 注意：实际还需考虑 NVLink/NVSwitch 拓扑，同节点内 8 卡可能也受拓扑影响；TP 过大时通信带宽可能成为瓶颈。
---
## Replica：服务副本数（数据并行）

Replica 是「完整可独立服务的最小单元」，包含完整的 Prefill+Decode 链路。

|实验名|replicas|总 GPU 计算|解读|
|---|---|---|---|
|所有实验|1|总 GPU = (P_workers×P_gpu + D_workers×D_gpu) × 1|当前所有实验都只部署了 1 套服务|

Replica 的作用：
- `replicas=2` 表示部署 2 套完全独立的 PD 服务，请求可负载均衡到任意副本
- 扩展 replica 是 水平扩容（Scale-out）提升 QPS 的标准方式

> ⚠️ 注意：
> - "1 套服务" = 1 组 Prefill 集群 + 1 组 Decode 集群（这就是 Disaggregated）
> - replica 表示需要多少组这样的「P+D 组合」
> - replica=2 时，P 节点数和 D 节点数都**直接乘 2**

## 不同框架的 Worker / Replica 映射关系
| 框架      | Worker 定义                                              | 资源粒度                                   | Replica 实现方式                                        |
| ------- | ------------------------------------------------------ | -------------------------------------- | --------------------------------------------------- |
| vLLM    | 1 个 Worker 进程 = 1 张 GPU 或 1 个 TP 组                     | `tp_size` 控制每个 Worker 的 GPU 数          | 启动多个 vLLM 服务实例，通过负载均衡器（如 nginx）分发请求                 |
| TRT-LLM | 使用 MPI rank 或 Triton Inference Server 的 instance group | `tensor_parallel_size` 定义 TP 组大小       | 通过 Triton Server 的 `instance_group` 配置多副本，或启动多个服务进程 |
| SGLang  | 与 vLLM 类似，1 个 Worker = 1 张 GPU 或 TP 组                  | `tensor_parallel_size` 控制 Worker GPU 数 | 启动多个 SGLang 进程，配合负载均衡器实现水平扩展                        |

### 各框架详细说明
#### 1. vLLM
```python
# 启动命令示例
vllm serve /model/path \
    --tensor-parallel-size 4 \      # 每个 Worker 用 4 卡做 TP
    --num-gpu-workers 2             # 2 个 Worker 并行处理请求
    --host 0.0.0.0 --port 8000

# Replica: 启动多个实例
# 实例1: vllm serve ... --port 8001
# 实例2: vllm serve ... --port 8002
# 配合 nginx/haproxy 做负载均衡
```

- Worker 映射：每个 Worker 是独立进程，通过 PyTorch 分布式进行 TP 通信
- Replica：需要手动启动多个服务实例，没有内置副本管理

#### 2. TRT-LLM (TensorRT-LLM)
```python
# 使用 Triton Inference Server 部署
# config.pbtxt 配置示例
instance_group [
  {
    kind: KIND_GPU
    count: 2    # 2 个副本
  }
]

# 或使用 mpirun 启动（单节点多实例）
mpirun -n 4 --allow-run-as-root \
    trtllm-build --tensor-parallel-size 4 ...
    trtllm-run --engine_dir=/path/to/engine
```

- Worker 映射：通过 MPI rank 管理多 GPU，使用 NCCL 做 TP 通信
- Replica：通过 Triton Server 的 `instance_group` 或启动多个进程实现

#### 3. SGLang
```python
# 启动命令示例
python -m sglang.launch_server \
    --model /model/path \
    --tp-size 4 \                 # 每个 Worker 4 卡 TP
    --num-workers 2 \             # 2 个 Worker
    --host 0.0.0.0 --port 30000

# Replica: 与 vLLM 类似，启动多个 SGLang 实例
```

- Worker 映射：继承自 vLLM 架构，Worker 是独立进程
- Replica：需启动多个实例，配合负载均衡器

### 框架选择建议：

- vLLM：生态成熟，文档丰富，适合大多数场景
- TRT-LLM：NVIDIA 生态，推理性能极致优化，适合对延迟敏感的场景
- SGLang：支持 RadixAttention（前缀缓存），适合多轮对话场景

## 三者关系+节点计算

```text
# Step 1: 先算单套服务（replica=1）的 GPU 需求
P_single_replica_gpus = prefill_workers × p_gpus_per_worker
D_single_replica_gpus = decode_workers × d_gpus_per_worker

# Step 2: 计算单套的节点数（单机 8 卡）
P_single_replica_nodes = ceil(P_single_replica_gpus / 8)
D_single_replica_nodes = ceil(D_single_replica_gpus / 8)

# Step 3: 乘以 replica 数量得到总节点数
P_total_nodes = P_single_replica_nodes × replicas
D_total_nodes = D_single_replica_nodes × replicas
total_nodes = P_total_nodes + D_total_nodes
```

- 示例
	- 假设配置：`prefill_workers=2`, `decode_workers=2`, `p_gpus_per_worker=4`, `d_gpus_per_worker=8`, `replicas=2`
		- 单套 P：2 × 4 = 8 GPU
		- 单套 D：2 × 8 = 16 GPU
		- replica=2 → P: 8×2=16, D: 16×2=32
		- P 节点：ceil(16/8) = **2 节点**
		- D 节点：ceil(32/8) = **4 节点**
		- **总计：6 节点**

⚠️ 边界情况：
- 假设所有 GPU 类型相同（同为 A100 或同为 L40）
- 假设机器都是 8 卡机型
- 异构场景（ P 用 L40，D 用 A100）需分别计算后再汇总节点
- 实际节点数还受机架拓扑、NVLink 连接性影响

## 配置建议
|目标|调整参数|注意事项|
|---|---|---|
|降低首 token 延迟 (TTFT)|↑ `prefill_workers` 或 ↑ `prefill_tp`|TP 过大（>8）会跨节点，收益递减|
|提升生成吞吐 (tokens/sec)|↑ `decode_workers` 或 ↑ `replicas`|优先加 replica，避免单副本 TP 过大|
|支持更大模型|↑ `gpu/worker` (即 tp)|确保 `tp ≤ 8`，避免跨节点通信瓶颈|
|节省节点资源|让 `workers × gpus_worker` 尽量是 8 的倍数|减少 GPU 碎片，提升集群利用率|
