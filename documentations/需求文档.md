## AI4S 场景容量评估数据需求说明

本文档用于向业务侧收集 AI4S 多 Agent 场景的**关键流量与配置信息**，供 `AIConfigurator (AIC)` 做以下工作：

- 在给定 **SLA 目标（TTFT / TPOT / 请求时延）** 和 **输入/输出长度** 的前提下，
- 基于已收集的硬件 + 引擎性能数据库，评估不同部署配置下的 **吞吐能力（tokens/s）与可承载并发**，
- 并给出在 **成本–性能** 维度上的推荐配置和帕累托前沿。

AIC **不会直接模拟真实线上排队和多轮对话的全部细节**（这些依赖实际到达过程与业务调度策略），
但会在上述约束下给出可靠的**容量规划和资源需求基线**，供业务侧决策“需要多少 GPU / 哪种配置组合”。

---

## 一、最小必填信息（AIC 可直接建模）

> 说明：下面字段是 AIC 做规模预测/成本分析的最小输入集。请按“字段：说明（单位）+ 示例”的格式尽量填写完整。

### 1. 业务流量 & SLA 需求（必填）

- **峰值并发（推荐）**
  - 含义：同一时间处于「处理中」状态的请求最大值（不含排队中的）。
  - 口径：建议按 **5 分钟时间窗内的最大并发** 统计。
  - 示例：`峰值并发 ≈ 800 req（5 min 窗）`
- **或：峰值 QPS（可选，二选一即可）**
  - 含义：每秒新进请求数（Requests Per Second）。
  - 口径：建议给出 **高峰时段的 P95 QPS**。
  - 示例：`高峰 P95 QPS ≈ 120 req/s`
- **日内波动情况**
  - 说明：是否存在明显高峰时段（例如白天 10:00–18:00），高峰时长大致区间。
  - 示例：`10:00–18:00 为高峰，峰值持续约 4 小时`
- **单次“科学任务”的交互模式**
  - 说明：一轮问答还是多轮对话；平均轮数。
  - 示例：`平均 3 轮对话 / 任务；少数任务会到 6 轮`
- **SLA 指标（单位：毫秒 ms）**
  - **首 token 时延 TTFT 目标**（推荐给出 P95）
    - 示例：`TTFT P95 ≤ 1500 ms`
  - **整轮完成时延目标**（如不方便给 TPOT）
    - 示例：`整轮时延（从发起到收到完整回复）P95 ≤ 8000 ms`
  - **或：TPOT 目标**（Time Per Output Token，单位 ms/token）
    - 示例：`TPOT P95 ≤ 20 ms/token`
- **排队容忍度**
  - 说明：是否允许请求在队列中等待，以及可接受的最大排队时间（单位 ms）。
  - 示例：`允许排队等待，排队时间 P95 ≤ 2000 ms`

### 2. 请求特征 & 文本长度分布（必填）

- **输入/输出 token 长度分布**
  - 口径：按「实际使用的模型 tokenizer 统计」，不是字符数。
  - 建议提供：P50、P95，或更细的分布（如直方图）。
  - 示例（单一场景）：
    - `输入长度：P50 ≈ 2k tokens，P95 ≈ 6k tokens`
    - `输出长度：P50 ≈ 800 tokens，P95 ≈ 2k tokens`
- **是否存在长上下文场景**
  - 说明：是否大量使用代码/文献等长上下文；最大/常见上下文长度。
  - 示例：`有，大量论文分析场景；上下文常见 16k–32k tokens，最大约 64k tokens`
- **主要使用场景（子业务）及占比（建议按“场景维度”同时给出 isl/osl + SLA）**
  - 说明：不同子业务如果对模型/配置要求不同，需要拆分建模。  
  对每个典型场景，建议给出：
    - 该场景占整体请求的比例；
    - 该场景的典型输入/输出长度（可用 P50/P95 近似 isl/osl）；
    - 该场景的 SLA 需求（TTFT / 整轮时延 / TPOT 要求）。
  - 示例：
    - 场景 A（写代码，短问答）：  
      - 占比：`约 40%`  
      - 文本长度：`输入 P50≈1k / P95≈2k；输出 P50≈300 / P95≈800`  
      - SLA：`TTFT P95 ≤ 800 ms；整轮时延 P95 ≤ 5s`
    - 场景 B（分析论文，长上下文）：  
      - 占比：`约 35%`  
      - 文本长度：`输入 P50≈8k / P95≈24k；输出 P50≈1k / P95≈3k`  
      - SLA：`TTFT P95 ≤ 2s；整轮时延 P95 ≤ 15s`
    - 场景 C（生成报告/总结）：  
      - 占比：`约 25%`  
      - 文本长度：`输入 P50≈4k / P95≈8k；输出 P50≈2k / P95≈4k`  
      - SLA：`更关注吞吐和成本，可接受整轮 P95 ≤ 30s`

### 3. 模型使用组合（必填）

- **各 Agent / 任务使用的模型及比例**
  - 示例：
    - `Agent_A：GLM-5，占 30% 任务`
    - `Agent_B：Kimi-K2.5，占 70% 任务`
- **是否存在多模型串联 / 并行调用（workflow）**
  - 示例：
    - `部分任务：先 GLM-5 做草稿，再 Kimi-K2.5 精修（串行，两轮调用）`
    - `有些任务并行调用两个模型，取交集结果（并行）`
- **模型分配约束**
  - 说明：是否有“某类任务必须用某个模型/某种精度”的强约束（比如科学计算对数值稳定性要求高）。
  - 示例：`数值敏感任务必须用 GLM-5 FP16，不允许量化`

### 4. 资源与成本约束（必填）

- **可用 GPU 机型 & 集群形式**
  - 示例：`当前主要使用 h200_sxm，支持 8/16/32 张卡一组；后续可能增加 b200_sxm`
- **预算约束**
  - 建议给出：
    - 单月总预算上限（按 GPU 小时或节点月租金）
    - 单次任务成本上限（如有）
  - 示例：
    - `单月 GPU 预算约 300,000 元（按 h200_sxm 单机月租金 30,000 元折算）`
    - `希望单次科学任务成本 ≤ 1 元`
- **能耗 / 节能要求（如有）**
  - 示例：
    - `希望控制在现有机房功率上限内，不再新增供电`
    - `对碳排有 KPI，优先考虑能耗更低的配置（在 SLA 满足前提下）`

## 二、建议补充信息（提升 AIC 预测精度）

### 1. 更细的流量形态

- 日/周内流量曲线（可提供汇总图或关键时间点数据）
- 高峰持续时长、突发流量（burst）场景描述

### 2. 更细的会话行为

- 不同任务类型的平均轮数分布（例如：简单问答 1–2 轮，复杂分析 4–6 轮）
- 是否存在「超长对话」（例如超过 10 轮）及占比

### 3. cache 与复用情况

- prefix cache / KV cache 是否会在业务层被重复利用
- 相似/重复请求的比例（便于后续考虑缓存命中优化）

### 4. 其它业务约束

- 对可用性/故障恢复的要求（是否需要多机房冗余）
- 是否有合规要求导致某些任务必须落在特定机器/集群

## 业务流量 & SLA 需求

- 峰值并发 or 峰值 QPS，及日内波动情况（是否有高峰时段）
- 单次“科学任务”的交互模式：一轮问答还是多轮对话？平均轮数？
- 关键 SLA 指标：
  - 首 token 可接受时延（TTFT）目标（如 P95 ≤ X s）
  - 整轮完成时延目标（如 P95 ≤ Y s）
  - 能否接受队列等待？最大可接受排队时间

## 请求特征 & 文本长度分布

- 历史请求日志（脱敏）：输入 token 长度分布、输出长度分布
- 是否有长上下文（代码/文献）场景？最大上下文长度约多少？
- 不同使用场景（子业务）的比例：比如“写代码”、“分析论文”、“生成报告”等，如果模型/配置可能不同，需拆分建模。

## 模型使用组合

- 各 Agent 对应使用的模型及其比例：
  - 比如 30% 任务用 GLM-5，70% 用 Kimi-K2.5
  - 是否会有“一个任务串联多个模型”的串行/并行调用（workflow）？
- 有无强制要求“某类任务必须跑在某种模型上/某种精度上”（比如科学计算对数值稳定性很敏感）。

## 资源与成本约束

- 业务可申请的 GPU 机型范围（纯H200？）
- 预算约束：单日/单月的大致预算上限，是否有“单次任务成本”上限，对应机型单机月租金
- 是否有能耗要求（例如功耗上限等）
